## Outcome

The chain «Мия, сделай карту по этому тексту» → `background.start` → job → MindWeaver `build_map` over hosted MCP → map generated by the
**user's model through Mia** → map in MindWeaver and tile data via `list_maps` runs automatically against a real Mia core (PostgreSQL, M50
AS, tool router, jobs worker, OpenAI-compatible API on real sockets; scripted model). Revoking MindWeaver in Mia's «Подключённые
приложения» makes MindWeaver's `/mcp` answer 401 and its model calls fail with a reconnect message. One thing needs Mia: the token
Mia sends to a `server.auth: mia_token` plugin (OI-M51-001/-002, requested diffs below); the E2E stands in for it with a real OAuth flow.

## Decisions

- Token check by `/oauth/userinfo`, not by decoding anything: Mia's access tokens are opaque and Mia has no introspection endpoint.
- Identity of a caller: Mia pairwise `sub` (per client) → else **verified email** of an existing non-local account → else 401.
- `build_map` runs with the *stored* grant of the user (needs `llm.generate`), not with the caller's bearer.
- `get_map` returns a light outline (title, ref, 240-char preview); the full text only through `get_node` (keeps the model's context small).
- No new Python dependency; `mcp` SDK not used. A Mia 401 on a `mia/*` call is never retried and marks the connection for reauth.

## Requested Mia changes (not made; owners M50/M15 files)

R1 `OAUTH_EXTRA_RESOURCES` (registered plugin servers as RFC 8707 resources), `app/modules/oauth/service.py` + `composition.py` + `app/core/config.py`:

~~~diff
 class OAuthConfig:
+    extra_resources: frozenset[str] = frozenset()  # from OAUTH_EXTRA_RESOURCES (comma list of https URLs)
     @property
     def resources(self) -> frozenset[str]:
-        return frozenset({base, base + "/", self.mcp_resource})
+        return frozenset({base, base + "/", self.mcp_resource}) | self.extra_resources
~~~

R2 `app/modules/oauth/principal.py` + `router.py::userinfo`: let `/oauth/userinfo` accept tokens bound to an extra resource and return their audience:
`expected |= config.extra_resources` when called from userinfo; `body["aud"] = access.resource` (if set) and `body["azp"] = access.client_id`.
MindWeaver already rejects a token whose `aud` is not its own `/mcp` (tested).

R3 `mia_token` source (OI-M15-009, option (a)): `ConnectionService.headers(..., auth="mia_token")` mints a 5-minute access token (no refresh) from the
user's **active grant of the plugin's own client** (`AuthorizationService.mint_access(user_id, grant, scopes={"openid"}∩grant, resource=server.url)`),
returns `{"Authorization": "Bearer …"}`, `None` (→ `connection_required`) without a grant. Needs an optional `remoteServer.clientId` (https URL of the
app's CIMD) in `plugin-manifest.schema.json`; then add `"clientId": "https://mindmapgen.xyz/api/auth/mia/client-metadata.json"` to `mia/mia.json`
(MindWeaver side, trivial). Same client ⇒ same pairwise `sub` ⇒ MindWeaver links the caller exactly; revoking the grant kills the minted token.

## Known limitations

- `/mcp` speaks only 2026-07-28 (no legacy `initialize`), has no rate limit; each `build_map` spends the user's Mia budget (OI-M51-003).
- Streaming calls (node chat) record tokens only: LiteLLM 1.53.7 drops Mia's `mia.cost_usd` from SSE chunks, so the ledger shows them
  «unpriced»; non-streaming generation (the map) has the exact cost. Mia's own spend log is complete.
- Token refresh in `astream` is a short blocking call on the event loop (only when the access token is within 60 s of expiry).
- Docker image does not copy `mia/ui` (the tile is bundled in the package; `resources/read` serves it only from a checkout).
