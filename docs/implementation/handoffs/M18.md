# M18 handoff

Branch `session/M18-feed`; `backend_head_commit` = last code commit, the handoff commit follows it.

## Outcome

`GET /v1/feed?before=<cursor>&limit=` returns the user's single main feed (voice and chat
together), newest first, with an opaque keyset cursor. Bearer and the M10 `mia_session` cookie
resolve to the same user; only the caller's own feed is reachable, a cursor of another feed is
`400 invalid_feed_cursor`, incognito runs never appear. Paging is exact while other runs write.

- `error-codes.json`: appended `invalid_feed_cursor` (400, not retryable, owner M18). Validation
  errors (`limit` out of range, empty `before`) are `422 validation_error`; unauthenticated

- Cursor (opaque, do not parse): base64url JSON `{c: feed_conversation_id, s: sequence, v: 1}`;
  means "entries with sequence < s". Bound to the user's feed, so another user's cursor cannot decode.

## Decisions

- Keyset on `entries.sequence`: allocated under the conversation row lock, so committed in
  order; new writes are always newer than any issued cursor, hence no gaps or duplicates.
- `GET` never creates the feed; no feed yet -> empty page, and any cursor -> 400.
- Cursor error is a new code `invalid_feed_cursor` (M12's `invalid_cursor` message mentions events).
- Only user/assistant text entries of the primary feed are listed (tool/system entries and
  non-feed conversations are not).
- `FeedService` for the router is built from the session factory with default windows (history needs none).

- Single feed only; no search, edit or delete; no tombstones for retention (OI-M12-001).
- `text` of an assistant item is the markdown of `display` (or speech); `speech`/`followups` stay
  in the entry and are not exposed.
- Items written by M16 job runs appear with `source: run_job` once the engine feeds them.
