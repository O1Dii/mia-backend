# S15-R1 handoff

## Outcome

Three separate defects made a healthy realtime session die for the same wrong
reason — it was quiet. A voice session now survives minutes of silence, a
vanished client releases its session slot immediately, and ordinary room noise
no longer ends the session. Verified against real Gemini on a physical
SM-S938B: 180 s held without failing, and a killed app's slot reusable at once.

## Defect 1 — silence read as provider failure

`_receive_connection` applied `idle_timeout_seconds` (90 s) to inbound traffic
only. While a user thinks, the client is still streaming microphone frames and
the assistant simply has nothing to say, so the adapter raised, and the gateway
answered `realtime_provider_unavailable`. For a voice assistant that is close to
the worst possible failure: the user pauses, the product breaks.

Idle now means quiet in *both* directions — the timeout only fires once the
client has stopped sending too.

Fixing it exposed a second-order bug. The read was `await asyncio.wait_for(anext(iterator), …)`,
and a timeout cancels `anext`, which closes the async generator. The connection
could therefore never survive an idle window: the next read raised
`StopAsyncIteration`, the loop treated it as a closed socket and tried to resume,
and resumption is impossible mid-stream. The read is now owned by a task that
survives the timeout.

## Defect 2 — a vanished client kept its session slot

Nothing in the gateway noticed a client that stopped talking; the socket stayed
open until the provider's own idle timeout fired. With
`MAX_ACTIVE_LIVE_SESSIONS_PER_USER=1`, a killed app therefore blocked the next
voice attempt for about 90 s.

A socket silent in both directions for `_CLIENT_INACTIVITY_SECONDS` (30 s) is now
closed with 1001 and its slot released. The symmetry matters: serving a response
counts as traffic, so a client listening to an answer is never cut off. No error
event is emitted — a vanished client cannot read one, and inventing a public
error code would change the realtime schema without an ADR.

## Defect 3 — room noise ended the session

Gemini's automatic activity detection opens a turn on its own VAD, so it can
start speaking before MIA's client commits one. When the client's local VAD
disagrees — ordinary room noise is loud enough for the cloud and not for the
phone — no commit ever arrives to drain `_deferred_messages`, and at 32 buffered
messages the adapter raised `too many messages arrived before input commit`.
Measured on the device: the session died about 30 s after connecting.

The oldest deferred message is now dropped instead. That is degradation, not a
cure: see Incomplete work.

## Decisions

- No new public error code for client inactivity: the realtime schema is frozen
  without an ADR, and a gone client cannot read an error anyway.
- Dropping deferred messages rather than enlarging the buffer: an unbounded
  buffer just delays the same failure, and the pre-commit backlog belongs to a
  turn MIA never acknowledged.
- The gateway keeps `asyncio.wait_for` while the adapter uses a task. A coroutine
  waiting on a queue is safe to cancel; an `anext` on a generator is not.

## Incomplete work

The underlying mismatch is that **two voice activity detectors are running against
each other**: MIA's contract is client-commit-driven (S25 controller, S26 local
VAD, barge-in by `response.cancel`), while the Live setup sends
`automaticActivityDetection: {disabled: false}`. Aligning them — disabling the
provider's detection and sending explicit activity markers around the committed
segment — is the real fix for defect 3. It changes the wire setup and can only be
judged with real speech, so it belongs to S31-R1.

  client commits.
