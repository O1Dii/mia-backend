# S16-R2 handoff

## Outcome

MIA was running two voice activity detectors against each other. Gemini's
automatic detection is now disabled and the turn is bounded by explicit
`activityStart`/`activityEnd` driven by the client's commit, which is what the
realtime contract always described. Proven against real Gemini: streaming speech
**without** committing now produces zero events, where the provider previously
answered on its own initiative.

## Root cause

S25's controller and S26's local VAD decide when a turn ends and send
`input.commit`; the whole realtime contract is built on that. But `_wire_setup`
sent `automaticActivityDetection: {disabled: false}`, so Gemini also decided,
using its own detector on the same audio.

When the two disagreed the session broke. Room noise is loud enough for the
cloud and not for the phone, so Gemini opened a turn, MIA never committed one,
the pre-commit deferral buffer filled, and the adapter raised `too many messages
arrived before input commit` — measured at about 30 s from connecting.
[S15-R1](S15-R1.md) stopped that from ending the session; this removes the cause.

The two real-Gemini runs are the substance of this repair: the same audio
produces a full answer when MIA commits and nothing at all when it does not.
That is the property the contract always assumed and never had.

## Decisions

- Disable the provider's detector rather than teach MIA to accept provider-driven
  turns. The client already owns the decision, S26 measured its latency, and
  barge-in is built on it; two detectors is the anomaly.
- `START_OF_ACTIVITY_INTERRUPTS` is kept. With manual detection an `activityStart`
  still interrupts a response in flight, so barge-in now actually reaches the
  provider instead of only suppressing output locally (OI-W6-017).
- The S15-R1 deferral drop stays as a safety net, though it should no longer be
  reachable.

## Incomplete work

None inside this repair. What it does not do is judge speech quality: whether the
client's VAD picks good commit boundaries in a real room is S31-R1's question,
and this change makes those boundaries the only ones that matter.

## Open issues

- OI-W6-017: barge-in now has two mechanisms — the client's local flush plus
  `response.cancel`, and the provider-side interrupt from `activityStart`. They
  should be measured together before anyone quotes a barge-in latency.

## Known limitations

- Verified with injected speech at normal levels, not acoustically. The protocol
  is proven; the microphone path is not.
- The Live guide recommends including audio context before `activityStart` and a
  silence threshold of at least 500 ms so natural pauses do not cut speech off.
  MIA opens the activity on the first captured frame and relies on S26's
  thresholds; whether those are generous enough is an acoustic question for
  S31-R1.
