# M41-R2 handoff

Branch `session/M41-R2-recipient-name` (worktree `mia-helper-wt/M41-R2`), base `e949dfc`. Nothing merged or pushed.

## Outcome

After «Петровой» the model calls `builtin.telegram.send_message {to: "person:<uuid>", text}` as `people.resolve`
tells it. The approval card (web, Android) and the voice prompt now read
`Telegram: send_message — to=«Яна Петрова (жена)», text="Надо купить молоко"` instead of `to="person:3e6c…"`.
`approval.arguments` and `args_hash` are unchanged (raw ref), so the decision and the execution are bound to exactly
what the tool receives. Web and Android are untouched: they already render `approval.summary`; the Android voice
cascade speaks the first 200 chars of it, and the named recipient is put **first** so the clipped phrase still says who.

## How it works

- `policy.ref_arguments(schema, arguments)`: a top-level string argument counts as a people ref only when the tool's
  own property schema documents refs (`person:`/`contact:` in its `description` or `pattern`; Telegram's `to` says
  "the ref (person:<id>, contact:<n>) or name"). Value is stripped (Telegram strips `to` too), ≤ 64 chars.
- `policy.approval_summary(..., names=)`: named arguments first as `key=«Имя (отношение)»`, then the rest exactly as
  before (sorted, JSON). Names are whitespace-collapsed, control chars removed, `«»` replaced, ≤ 120 chars; the whole
  text stays ≤ 500. Without names the text is byte-identical to M13.
- `McpToolRouter.bind_ref_names(resolver)` (late binding, like `bind_device_access`) and `_ref_labels` in
  `_request_approval`: only for **core tools and in-process plugins** (they resolve refs through Mia); a remote server
  receives the opaque ref, so its card keeps the ref. Lookup uses the run's `user_id`/`run_id`; any resolver error →
  warning `approval_ref_names_failed`, raw ref on the card, approval proceeds.
- `app/modules/memory/names.py` `MemoryRefNames` (port `RefNameResolver`): `person:<uuid>` (canonical form only, the
  same comparison Telegram's host makes) → the owner's **active** person (`MemoryService.people_by_ids`, new, one query,
  no key creation, not an access-log entry: it is the owner's own screen, not a model read); `contact:<n>` → the
  per-(owner, run) `ContactsCache` that `people.resolve` and the Telegram host share. Returns only display name +
  relation (or «контакт телефона»), through `minimize` — never phones/e-mails/handles/ids. Unknown, foreign, deleted or
  malformed refs are absent → raw ref.
- Wiring: `build_memory_stack(..., tools=)` binds the resolver right where it registers the memory core tools, so
  `app/composition.py` needed **no** change (the card allowed one line there; this avoids a conflict with M17-R1).

## Decisions

- Name only arguments the tool documents as refs (schema description/pattern), never any string that looks like a ref:
  otherwise `text="person:<id>"` would show a name while the friend receives the literal ref.
- Only core and in-process tools: the card must match what executes; a remote server gets the opaque ref.
- Named recipient first in the summary (voice prompt is clipped at 200 chars on Android).
- Relation shown next to the name («Яна Петрова (жена)») so two same-named people can be told apart; phone contacts say
  «контакт телефона».
- Binding inside `build_memory_stack` instead of a line in `app/composition.py` (same effect for every composition that
  builds memory with a tool stack, no shared-file touch).
- `people_by_ids` is not written to the memory access log (owner's own screen; `person_identifiers`, used by the
  Telegram host, does not log either).
