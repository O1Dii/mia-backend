# S17-R1 handoff

## Outcome

Every real Gemini turn failed — text and voice alike — because MIA handed the
provider a raw Pydantic JSON Schema for its tool declarations. Both Gemini
surfaces reject the keys that schema carries. Tool schemas are now translated at
the provider boundary, and both surfaces were verified against the live API.

## Root cause

`ToolDefinition.parameters` is provider-neutral and the registry builds it with
`CurrentDatetimeArguments.model_json_schema()`, which emits `additionalProperties`,
`title` and (for nested models) `$defs`/`$ref`. Gemini's `Schema` type is an
OpenAPI 3.0 subset that defines none of those:

- the Gen AI SDK validates `FunctionDeclaration.parameters` and raised
  `ValidationError: parameters.additionalProperties Extra inputs are not permitted`
  before any request left the process, so `GeminiTextAIProvider.stream` emitted
  `ProviderError` and the Android chat showed "Provider request failed.";
- the Live wire API refused the setup frame, so `configure()` raised
  `GeminiLiveAdapterError` and no voice session could connect at all.

The defect appeared the moment the W4 integrator wired `tools=registry.declarations()`
into both adapters, and it is invisible without cloud credentials.

## Why the suite missed it

Every provider fixture declared `parameters={"type": "object"}` — a schema that
happens to contain nothing Gemini rejects. No test used the real registry
declaration, so the mapping was never exercised with a realistic schema.

## Changes

| Repository | Paths | Summary |

| mia-helper | `app/providers/ai/tool_schema.py` | New `to_gemini_schema`: keeps the documented OpenAPI subset, inlines `$ref` from `$defs`, expresses `const` as a one-value enum, drops the rest. |
| mia-helper | `app/providers/ai/gemini_text.py` | `FunctionDeclaration.parameters` is translated instead of passed through. |

| mia-helper | `tests/providers/test_tool_schema.py` | 10 tests driving the real registry declaration. |

Translation lives in the adapters, where the mapping to each wire format already
lives, so the registry stays provider-neutral.

## Decisions

- Translate per adapter rather than changing the registry: provider constraints
  do not belong in a provider-neutral contract.
- Allow-list the supported keywords rather than deny-list the known-bad ones, so
  a future Pydantic keyword cannot silently reach the wire.
- `$ref` is inlined (depth-bounded) so nested argument models survive instead of
  collapsing to an empty object. No tool uses one yet; the PoC tool is flat.

## Known limitations

- `to_gemini_schema` is verified against one flat tool schema plus synthetic
  nested cases. A tool with `allOf`/`oneOf` would lose those keywords silently;
  the allow-list drops them rather than failing loudly.
