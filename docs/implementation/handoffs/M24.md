Android branch `session/M24-web-push` (3 commits on `fbc3e1a`).

## Outcome

Android opens the MIA web app inside the app: a row of entries above the chat (Магазин, Мои плагины, Дашборд, Что Мия знает,
Подключения) opens one page in an isolated WebView that is signed in with the app's bearer (no web login screen). A push about
a finished background job posts a notification; its tap (warm or cold start) opens a native card with the result and marks the
inbox item read. The FCM token is registered through `PUT /v1/devices/push-token`. Device gate on SM-S938B passed (details below);
live FCM through Google was not possible (no Firebase project) and is a user check.

## Contracts produced or changed

- `POST /v1/auth/web/handoff` (bearer only; cookie → 403) body `{path?}` → 201 `{code, expires_at, redeem_path}`, `Cache-Control: no-store`.
  Each call (even with the same `Idempotency-Key`) mints a new code, nothing is replayed.
- `GET /v1/auth/web/handoff/redeem?code=` (no auth) → 303 to the path bound to the code + `Set-Cookie: mia_session` (HttpOnly,
  SameSite=Strict, same policy as web sign-in); `Referrer-Policy: no-referrer`. Invalid/used/expired → 401 `web_handoff_invalid`.
- Code: 256 bits, only SHA-256 stored in Redis (`auth:web-handoff:<hash>`, value user id + landing path), TTL 60 s, single use via
  `GETDEL`. No migration. Landing path is bound at issue time, not taken from the redeem URL, so there is no open redirect; it must be
  `/<root>[/…][?query]` with root in `chat, store, installed, models, approvals, dashboard, memory, inbox, privacy`, no scheme/host/`//`/`\`/
  `#`/dot segments/encoded separators, ≤512 chars; else 400 `web_handoff_path_invalid`. Rate limits: issue per IP and user
  (`AUTH_AUTHENTICATED_RATE_LIMIT`), redeem per IP (`AUTH_EXCHANGE_RATE_LIMIT`).
- New error codes `web_handoff_invalid` (401), `web_handoff_path_invalid` (400), owner M24.
- Android ↔ backend: unchanged M16 contract (`PUT /v1/devices/push-token`, FCM `data.type == "inbox_item"` keys, `GET /v1/inbox`, `POST /v1/inbox/{id}/read`).
- Android public API: `WebSurfaceScreen`, `WebSurfaceLoader`, `WebNavigationPolicy`, `InboxCardScreen`, `PushRegistrar`, `PushPayload`.

## Decisions

- Redis, not a table, for the codes: short-lived, atomic `GETDEL`, no migration. Landing path bound to the code.
- The web is expected on the backend origin (production) or `miaWebBaseUrl` (dev proxy); the redeem URL is resolved against the web origin and refused if the host differs.
- WebView: JavaScript on (React SPA), no `addJavascriptInterface` at all (the page cannot call the app; a unit test greps for it), navigation limited to the web origin,
  other http(s) links go to the system browser, other schemes dropped, embedded frames may load https only, file/content access off, no mixed content, camera/mic/
  geolocation/file chooser denied, no new windows, no third-party cookies. «Only explicitly allowed actions» = none are needed, so none exist.
- Every open/reload/retry asks for a fresh code (codes are single use); a 401 from the app's own session shows «Войдите снова».
- The tray notification FCM shows itself (notification+data message, app in background) carries the data as intent extras, so `PushPayload.fromIntent` accepts both
  our action and the launcher intent with `type=inbox_item`; the card only trusts the id and loads everything else from the server.
- Entries live in the chat's `banner` slot (no change to `feature/chat` or `feature/settings`).
- The result card is native (`MiaDisplayCard`, Markdown via `ChatMarkdown`); `Display.App` shows its fallback.
- Notification permission is requested once after sign-in when push is configured.

## Known limitations

- Web header (brand, tabs) of the SPA shows under the native top bar; the SPA has no "app mode".
- A web session created by a hand-off is not revoked by the app's sign-out (OI-M24-004); the WebView data is cleared locally.
- Dashboard/Memory entries depend on M31 routes; the inbox list is not a screen in the app (push card only).
- Foreground `onMessageReceived` posts our notification; with the app in the background the system tray one is shown by FCM (no deduplication needed, never both).
