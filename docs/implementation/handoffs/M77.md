## Outcome

The user decides where Mia's notifications go (OI-M41-002 DECIDED). The inbox always gets every item; a new user also gets push
only. Every other channel is off until the user switches it on or answers the question that a newly connected channel asks (the
Telegram bot: «Присылать сюда уведомления Mia?» with the inline buttons «Да» / «Нет»). Settings are a switch per channel plus a
table «event type × channel» for timers & alarms / job results / approvals / plugin messages, shown on a new web page
«Уведомления». Timers, reminders, job results, `notify` and a background run that waits for approval are routed by those settings;
an explicit `delivery.channels` still wins; a channel that cannot reach the user ends its delivery `skipped` with the reason.
A timer of a user who said «Да» arrives in the bot (fake Bot API, DoD test). Verified: full pytest 1513 passed / 6 skipped,
full Playwright 90 passed / 2 skipped, ruff, format, mypy, contracts validator, migration up/down/up + `alembic check`, tsc, build, Prettier.

## Scope completed

- **Routing core** (`app/modules/notifications/preferences.py`): `resolve_channels(session, user, event_type)` =
  channels switched on (default: push only) ∩ cells of the table (default: on). Called inside the transaction that creates the
  inbox item, so the item and its deliveries stay atomic. `NotificationPreferences` service (`snapshot`, `update`, `route`,
  `decided`, `decide`, `forget`) is `app.state.notifications.preferences`.
- **Event types**: `timer_alarm` (plugin deadlines — timers, alarms, focus — and `reminder`-kind jobs/schedules), `job_result`
  (job results/failures, `notify` called inside a job), `approval` (a background run waits for confirmation), `plugin_message`
  (`notify` from Mia/plugins/apps, `POST /v1/notify`).
- **Explicit channels win**: `channels_of(delivery)` (jobs/service.py) returns the requested channels or `None`; `None` is stored
  as `delivery = {"channels": ["inbox","push"], "auto": true}` and resolved when the job finishes (`jobs/chats.py:delivery_channels`).
  `POST /v1/schedules` and `schedule.create` accept no `delivery`. The model tools' descriptions now say «pass delivery only if the
  user names a channel» (changes `tools_digest` of the core tools, nothing else).
- **Channel registry** (`channels.py`): names open to plugins (`[a-z][a-z0-9_.:-]{0,47}`, not `inbox`); optional `label` and
  `async connection(user_id) -> ChannelConnection(connected, detail)`; `ChannelRegistry.connection/label`. Built-ins: push
  (`push_not_configured`, `no_push_token`), Telegram (`not_linked`); an unregistered known channel reports `not_configured`.
- **Telegram bot**: after `/start <token>` it sends «Готово: Telegram подключён к Mia.» and the question with buttons; `callback_query`
  «Да/Нет» (only the linked Telegram user) saves the answer, answers the callback and edits the message; `/stop`, the app's
  `DELETE /v1/telegram/link` and a blocked bot **forget** the answer (the next link asks again); `/start` without a token from a
  user linked before M77 asks once. `TelegramBotApi` gained `buttons`, `answer_callback`, `edit_message`; `setWebhook` now allows
  `callback_query` (**re-register the webhook on deploy**, OI-M77-001).
- **Background approvals**: the job runner posts an `approval` item («Нужно подтверждение», the task goal) when a run enters
  `waiting_approval` (OI-M77-002 for what is not covered).
- **Web «Уведомления»** (`/notifications`; links in «Ещё» and the inbox header): inbox row «Всегда», channel rows with
  «Подключён / Не подключён» + the reason and what to do, a switch each, the table (cells of an off channel are locked, values kept),
  optimistic updates with last-answer-wins, scroll box for the table on a phone.
- **Manifest extension point**: `provides.notificationChannel {id, label, description?}` (schema + example `channel.mia.json`; no
  runtime adapter yet, OI-M77-003).

## Decisions

- **Defaults** (user decision, OI-M41-002): code never adds a channel; no stored answer = Telegram off, push on, every table cell on.
  A new channel asks itself; disconnecting forgets the answer.
- **Storage**: sparse rows (only what the user chose) instead of one JSON blob: plugin channels need no schema change and a
  default can change without a data migration.
- **Explicit channels** are about the *result*; the approval notice and the Telegram-chat result card follow other rules: a result
  for the Telegram chat is still sent to Telegram (it answers a question asked there), an approval notice always follows the settings.
- **Unavailable channel** keeps the M16 behaviour: a delivery row ends `skipped` with the reason (`channel_not_connected`,
  `push_not_configured`, `no_push_token`) — visible, not silently dropped; the settings screen shows the same reason up front.
- **`notify`**: from inside a job it is a `job_result`, otherwise a `plugin_message`.
- **Optimistic UI** on the page: a click updates the screen at once; only the answer to the last request is shown (changes are merges).
- **`PATCH` + `Idempotency-Key`** like the other mutations; booleans are strict (`"yes"` is a 422).
- The device-consent FCM push (M70) is functional, not a notification, so it ignores these settings (OI-M77-002).
