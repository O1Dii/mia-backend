## Root cause (UC-MW5b-live, item 1)

«Сделай подробный отчёт … и пришли, когда будет готово» → `background.start` with the goal in the user's words. The job's
model read «пришли» and called `notify` with the report. Since M77 `notify` inside a job is a `job_result`: it created an
inbox item and push **immediately**, while the job stayed `running` (the run continued for one more model turn). The run's
final reply «Отчёт готов, уведомление отправлено» then became the job result → `store.finish` posted a second card, a
second inbox item and a second push, and only then the job turned `succeeded`. In «Входящие и задачи» the job result
(the record that belongs to the job) held only that one-line ack, so there was nothing to expand.

## Fix

- `notify` inside a job (`JobTools._note`) delivers nothing: it appends `{text, title?}` to `jobs.notes` (new column,
  only while that run is the job's current run, ≤ 20 notes) and tells the model the text joins the single result.
- `JobRunner._conclude` folds the notes into the final answer (`messages.with_notes`): text/card display → notes above its
  markdown (unless already contained); speech-only ack → the notes become the result (display + speech from them);
  app/link display kept. Failures carry the notes in the failure item («Что успела подготовить»).
- `store.finish` sets `succeeded`, creates **one** inbox item with its deliveries and **one** card in the source chat in
  the same transaction; notes are cleared (also on retry/reclaim). `notify` no longer counts as an external write of a
  job run (`_run_wrote`), so it does not block a retry.
- Prompts: `job_prompt` and the `job` profile say the final answer is delivered once by Mia even when the task says
  «пришли/сообщи», do not call `notify` for it; the `notify` tool description says the same (changes the core
  `tools_digest`, nothing else). `notify` outside jobs is unchanged (M77).
- Card ↔ inbox: the card is posted after the inbox item and names it (`FeedCard.inbox_item_id`).

## API / contract additions (all additive) — for M75-R1 and M76-R1

- `GET /v1/feed`: `FeedItem.steps` (assistant items only, 1..32, call order, absent when no tools) — `FeedStep`
  `{tool_call_id, tool, plugin_id?, risk?, executor?, status, arguments?, error_code?, error_detail?, approval?}`,
  `status ∈ running|succeeded|failed|denied|expired|uncertain|cancelled`, `approval = {id, status, summary,
  decided_at?, channel?: web|android|voice_trusted, device_id?}` (`FeedStepApproval` in openapi). Exactly the plan's
  contract. `arguments`/`error_detail` are those of `tool.call.started/completed` (redacted by M73). A **job result card**
  carries the steps of the job's run (approvals decided on the phone during a background task show up in web).
  A call without `tool.call.completed` in a finished answer is `uncertain`.
- `FeedCard.inbox_item_id` (new cards only): open `GET /v1/inbox/{item_id}`.
- `GET /v1/inbox/{item_id}` → `InboxItem` (404 `inbox_item_not_found`), bearer or cookie.
- `InboxItem.text`: the full text to show expanded (display markdown / app fallback / link as markdown / else speech) —
  for a job it is the whole report. `response.display` is unchanged (also full).
- `error-codes.json`: `job_notes_unavailable` (event-only, owner M74).
- Client rule: render steps from `FeedItem.steps` on history load; live events still update the newest answer.

## Decisions

- OI-M74-R1-001 (DECIDED): `notify` inside a job drafts the single result (rules above; options rejected in the inbox).
- OI-M74-R1-003 (DECIDED): steps on job cards from the job's run; `FeedCard.inbox_item_id`; `InboxItem.text`.
- Steps are read at feed time (no new table): 3 batched queries per page (run events of the page's runs joined to
  `runs` for the owner, their approvals, the runs of cards' jobs). Payload is read whole per event; events are bounded by
  the profile's tool-call limit.
