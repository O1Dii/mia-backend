## Outcome

`server.auth: mia_token` works end to end: MindWeaver's package is published with `cli.mia_plugin`, installed from Mia's
store, connected through the user's «Войти через Mia» grant, and every router call carries a 5-minute token Mia mints from
that grant; revoking the app in Mia stops it at once. «Add by URL» of `https://mindmapgen.xyz/mcp` completes with Mia as the
authorization server. The M51 strict xfail is gone: MindWeaver E2E 7 passed, 0 xfail.

## Scope completed

- **R1** `AuthorizationService.resource_allowed`: own API/`/mcp` + `OAUTH_EXTRA_RESOURCES` (any client) + `ResourcePolicy`
  `app/modules/connections/resources.py::PluginResources` (canonical URL match, no config needed):
  release `server.url` → allowed for the release's `server.clientId` or Mia's connection client (no `clientId` → Mia's client only);
  `installations.custom_url` (add by URL) → Mia's connection client only. Everything else `invalid_target`.
- **R2** `/oauth/userinfo` (`AppAuthenticator.authenticate(any_audience=True)`) accepts tokens of any issued resource and returns
  `azp` (client) and `aud` (resource, when bound). `/v1/*` and `/mcp` still refuse a plugin-audience token.
- **R3** `AuthorizationService.mint_plugin_token` (access only, `min(OAUTH_PLUGIN_TOKEN_TTL_SECONDS, access TTL, 300)`, scopes ∩ live
  grant, row tied to the grant) and `plugin_grant`; `ConnectionService`: `POST /v1/connections` for `mia_token` → grant check →
  `PluginConnection(auth_method="mia_token", no secret)` + installation `active`, `200 {connection_id, status: connected}`, or
  `409 connection_sign_in_required` (`details.client_id`); `headers(auth="mia_token")` mints per call (`openid` only), `None` →
  `connection_required` without connection/grant or when the manifest's url/clientId no longer match the connection.
- Publication: `mia_token` requires `server.clientId`, https on a host in `permissions.network` (http loopback only with
  `OAUTH_ALLOW_LOOPBACK_CLIENTS`); `clientId` refused for other auth kinds (`catalog/validation.py::client_id_problems`).
- MindWeaver: `mia/mia.json` `clientId`; `/mcp` refuses an audience-less token whose `azp` is another app (hardening enabled by R2).

## Contracts, config, data

- Schema: `remoteServer.clientId` (uri, ≤255, `^https?://`). OpenAPI: `startConnection` `200 {connection_id, status}`;
  `oauthUserinfo` `azp` (required) + `aud`. Error code `connection_sign_in_required` (409, owner M51).
- Config: `OAUTH_EXTRA_RESOURCES` (comma list; https only outside local), `OAUTH_PLUGIN_TOKEN_TTL_SECONDS` (30–300, default 300).
- No migration: minted tokens are `oauth_tokens` rows (`kind=access`, own family, no code); mia_token connections are
  `plugin_connections` rows with `auth_method='mia_token'` and no ciphertext.

## Decisions

- R1 derives the allowed set from vetted data (admin-published releases, the user's own add-by-URL rows) and binds it to clients,
  so a third-party app can never get a token whose audience is a plugin server; the env list stays only as a dev override.
- Minted token carries `openid` only (∩ grant): the plugin needs identity; same client ⇒ same pairwise `sub` as its sign-in.
- Connect is explicit (409 → sign in to the app → connect again); afterwards revocation is lazy: no grant ⇒ `connection_required`,
  installation stays `active` and recovers when the user signs in again. Disconnect never touches the app grant.
- Mint per call, no cache (OI-M51-R1-003). Add-by-URL with Mia as AS keeps the generic OAuth path (OI-M51-R1-002).
