# S25-R2 handoff

## Outcome

A close the server started never reached the client at all. The gateway ended an
idle session with 1001 and the voice screen stayed on "waiting" indefinitely —
no error, no retry, nothing but leaving the screen. The close is now surfaced,
and the controller turns it into the retryable error it always knew how to
produce.

## Root cause

OkHttp invokes `onClosed` only after the client answers the peer's close frame.
`OkHttpRealtimeClient.Listener` overrode `onClosed` but not `onClosing`, and
never answered, so for a server-initiated close neither callback fired: no
`RealtimeInboundEvent.Closed` was ever emitted and the event channel stayed open.

The controller was not at fault. `handleInbound` already maps `Closed` to
`fail(..., retryable)` from any state other than `Closing`; it was simply never
given the event. That is why the defect looked like a state-machine bug and was
not one.

Observed in W6 after [S15-R1](S15-R1.md) taught the gateway to hang up on a
socket silent in both directions: the server closed, and the device carried on
showing "waiting" for the remaining three minutes of the run.

| mia-helper-android | `feature/voice/src/test/.../RealtimeVoiceControllerTest.kt` | `WaitingForResponse` does not outlive its socket. |

The handshake is answered with 1000 rather than echoing the peer's code: some
close codes are reserved and cannot be sent back, and a plain acknowledgement
carries no information the peer needs.

## Decisions

- Fix the transport, not the controller. The controller's handling was already
  correct, and adding a timeout there would have papered over a socket that was
  genuinely dead.
- `finish(code)` is idempotent because a close legitimately arrives twice, and a
  client-initiated close already marks the connection terminal, so the client's
  own shutdown path is unaffected.

## Known limitations

- This fixes a close the peer initiates. An abruptly severed connection still
  relies on `onFailure`, a separate path that was already working and was not
  touched.
- The device runs surfaced an unrelated instability, recorded as
  [OI-W6-019](../OPEN_ISSUES.md): voice sessions sometimes end on their own
  after 7–45 s. This repair is what makes that visible rather than causing it —
  before it, such a session simply hung.
