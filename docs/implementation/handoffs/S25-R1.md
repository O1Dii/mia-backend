# S25-R1 handoff

## Outcome

Real Gemini response audio failed every voice turn about 26 ms after
`response.audio.started`: the controller treated a full playback jitter buffer as
a failed turn. A full buffer is now ordinary backpressure, and the two results
that mean "the response went away" stopped being fatal.

## Root cause

`AudioEngineConfig.playbackBufferDurationMillis` is 240 ms, which at 24 kHz PCM16
is 11,520 bytes. Gemini Live streams a response considerably faster than it
plays, so the opening frames fill that buffer before `AudioTrack` has drained
anything. `RealtimeVoiceController.handleAudio` mapped `BUFFER_FULL` straight to
`fail("Playback buffer is full", retryable = true)`.

The buffer is deliberately small — S26's barge-in flushes it — so enlarging it
would trade away the interruption latency the design is built around. The
correct response is to wait.

A second, latent problem sat in the same `when`: `NO_ACTIVE_RESPONSE` and
`STALE_RESPONSE` fell into the `else` branch and failed the session *fatally*
with "Invalid realtime playback audio". After a flush or a finished response
those are the expected answers, and once the handler could suspend they became
reachable on the normal barge-in path.

## Why the suite missed it

`FakeAudioEngine.offerPlayback` always returned `ACCEPTED`, so no test ever put a
non-accepting result through the controller.

## Changes

| Repository | Paths | Summary |
| --- | --- | --- |
| mia-helper-android | `feature/voice/.../RealtimeVoiceController.kt` | `handleInbound`/`handleAudio` suspend; `BUFFER_FULL` waits in 10 ms steps up to 5 s; `NO_ACTIVE_RESPONSE`/`STALE_RESPONSE` count a stale frame and return; `ENGINE_CLOSED` returns; only malformed audio is fatal. |
| mia-helper-android | `feature/voice/src/test/.../RealtimeVoiceControllerTest.kt` | `FakeAudioEngine` can reject a scripted number of offers; two tests cover drain-and-continue and never-drains. |

The wait re-checks the active response each iteration, so a cancelled response
drops its queued frame instead of waiting the timeout out. Not consuming the
inbound event also backpressures the gateway, which is what the bounded event
path is for.

## Decisions

- Wait rather than enlarge the buffer: the small jitter buffer is what makes
  S26's 83 ms flush possible, and the realtime contract caps it at 500 ms anyway.
- 5 s is a generous ceiling — playback drains in real time, so a buffer that has
  not moved in 5 s indicates a stalled `AudioTrack`, not a fast producer.
