# S25-R3 handoff

## Outcome

Voice sessions were dying 7–45 seconds in, and the cause was [S25-R1](S25-R1.md)
— a repair made earlier in this same wave. A response's audio now waits in a
queue of its own instead of inside the inbound event stream. Three consecutive
spoken turns then completed on a physical SM-S938B against real Gemini without
the session ending, where before the fix it died on the first answer.

## Root cause

S25-R1 correctly stopped a full playback jitter buffer from failing the turn, and
made it wait instead. It waited in the wrong place: inside the
`newConnection.events.collect { … }` lambda.

That lambda is the consumer of `OkHttpRealtimeClient`'s 32-slot inbound channel.
Gemini streams a response considerably faster than it plays, and the jitter
buffer holds 240 ms, so the wait was not exceptional — it happened on every real
answer. While it waited the channel stopped draining, filled, and `offerEvent`
did what it is written to do:

~~~kotlin
if (eventChannel.trySend(event).isFailure) {
    webSocket.close(BACKPRESSURE_CLOSE_CODE, "client event queue full")
}
~~~

The client closed its own socket with 1013. Everything observed in
[OI-W6-019](../OPEN_ISSUES.md) follows from that: the gateway logged no
`close_code` because it never closed anything, no server `_fail` ran, and the
next `interrupt()` reported `Could not interrupt the realtime response` because
`cancelResponse` returns `WebSocket.send`, which is false on a closing socket.
The barge-in failure was a symptom two steps downstream of the cause.

It stayed hidden until [S25-R2](S25-R2.md) taught the client to surface a closed
socket. Before that the session simply hung.

## Changes

| Repository | Paths | Summary |
| --- | --- | --- |
| mia-helper-android | `feature/voice/.../RealtimeVoiceController.kt` | `handleAudio` no longer suspends; audio goes to a bounded `pendingPlayback` channel drained by its own coroutine, which keeps S25-R1's wait. A barge-in discards what is queued. |
| mia-helper-android | `feature/voice/src/test/.../RealtimeVoiceControllerTest.kt` | A control event behind a backpressured audio frame must still be handled. |

`PENDING_PLAYBACK_FRAMES = 512` is roughly forty seconds of 4 KiB output frames.
Overflowing it means playback has stopped draining, which is a real failure and
still fails the turn retryably; a long answer buffered ahead of playback is
ordinary and must not.

## Decisions

- Give the audio its own queue rather than enlarge the jitter buffer or the
  event channel. The jitter buffer is small so barge-in can flush it, and the
  event channel's bound is a deliberate protocol safeguard — neither should
  absorb a whole response.
- Keep the 1013 close in the client untouched. It behaved correctly; it was
  reporting a real stall that should not have existed.
- A barge-in drains the pending queue, so a retired response cannot resume
  playing after the user has interrupted it.
