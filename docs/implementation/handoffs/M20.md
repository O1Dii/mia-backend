Android branch `session/M20-assistant-vis` (worktree `mia-helper-android-wt/M20`), coordination branch `session/M20-coordination`. `backend_head_commit`/`coordination_commit` = the handoff commit of the coordination branch (filled by the integrator). ## Outcome

Mia can be registered as the system digital assistant: `MiaVoiceInteractionService` + `MiaVoiceInteractionSessionService`/`MiaVoiceInteractionSession` are declared (merged APK verified with `aapt2`), the assist gesture opens the existing voice screen through the launcher activity, a settings-page screen and a dismissible banner request/restore `ROLE_ASSISTANT`, and the lock-screen path shows voice over the keyguard while every other route is gated behind the credential prompt. 96 JVM tests pass (22 new in `feature/assistant`, 4 manifest-contract in `app`); on SM-S938B the role was assigned via the system picker, the assist button opened the Mia voice screen unlocked and over a secure lock screen.

## Scope completed

- VIS + session service + session (UI-less: hands over to the app via `startAssistantActivity`, then disables its own window). `onReady` disables assist structure and screenshot (Mia does not read the screen). `onLaunchVoiceAssistFromKeyguard` -> `showSession`.
- Role request: `AssistantRoute()` screen (opens `ACTION_VOICE_INPUT_SETTINGS`; the role dialog is not available for assistants) refreshing on resume and activity result; `AssistantRoleBanner` on the conversation list (hint), "Digital assistant" button in Settings.
- Role-loss detection: `AssistantRoleMonitor` (Active / Lost / NotAssigned) with per-install memory in SharedPreferences. A hint is shown for Lost and NotAssigned, dismissible, re-armed when the role is regained. Uninstall clears memory (backup is off) so a reinstall reads as NotAssigned with the same hint.
- Lock screen: `LockedAssistSession` + `AssistantLockScreen`: on a locked device the launcher activity calls `setShowWhenLocked(true)`, the back stack is reset to voice only, any other route (incl. sign-in) calls `requestDismissKeyguard`; denial finishes the activity; `onStop` clears show-when-locked.
- `MainActivity` handles `by.mia.assistant.action.VOICE_ASSIST` and `android.intent.action.ASSIST`.

## Decisions

- Session has no UI of its own; it starts the existing app (voice screen) via `startAssistantActivity` and calls `setUiEnabled(false)`. Keeps M22 free of a second UI.
- Lock-screen policy: voice may run over the keyguard (token store is not unlock-bound); nothing else is reachable without `requestDismissKeyguard`. The launch intent's lock state is never trusted: `MainActivity` reads `KeyguardManager`.
- `MiaRecognitionService` stub (always `ERROR_CLIENT`, no `RecognitionService` intent-filter) is only there because VIS metadata requires one (OI-M20-002).
- Scope note: the card allows manifest "service entries only", but a launch needs the activity side. Minimal extra edits outside the strict scope: `MainActivity` intent-filters (manifest), `MainActivity.kt`, `MiaApp.kt`, new `AssistantEntry.kt` (all additive; `MiaApp` has a new defaulted parameter `assist`). If the integrator prefers, M22 can fold them into its voice work.
- ROLE_ASSISTANT cannot be requested with `createRequestRoleIntent`; the screen opens the system assistant page instead (device-verified).
- Wake word and tile/widget are not implemented (out of scope / Review §6.1 "trivial", not in card).
