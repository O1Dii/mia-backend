# S13-R1 handoff

## Outcome

With [S17-R1](S17-R1.md) in place the model finally called a tool for real — and
the turn still failed. The whole Gemini 3.x family rejects the continuation turn
MIA builds after a tool runs. `gemini-2.5-flash` accepts it, the supported model
families are now pinned in the environment template, and the full tool loop was
proven on a physical device against real Gemini.

## Root cause

MIA's manual loop rebuilds the `functionCall` part from its provider-neutral
`ToolFeedback` (name + arguments). Gemini 3.x additionally requires the
`thought_signature` it emitted with the original call to be echoed back:

~~~text
400 INVALID_ARGUMENT: Function call is missing a thought_signature in
functionCall parts. This is required for tools to work correctly.
~~~

`ToolFeedback` carries no such field, so the continuation is always rejected.
The visible symptom was the worst kind: the tool ran, the executor audited it
`succeeded`, the UI showed "Tool succeeded", and then the turn failed with
"Provider request failed."

Measured: `gemini-2.5-flash` PASS; `gemini-3.5-flash` and `gemini-3.8-flash`
both 400.

## Why the suite missed it

Every deterministic provider test drives a stub `models` object, so no test ever
reaches the API. The tool-feedback tests assert the *shape* MIA sends, which is
exactly the shape Gemini 3.x rejects.

## Decisions

- Pin the model family rather than implement signature passthrough. The
  passthrough is the right long-term fix but it changes a provider-neutral
  contract, which belongs in a planning cycle, not a repair.
- The new smoke is credential-gated like S16's Live smoke, so it skips in CI and
  runs where credentials live.

  here on quality or cost differences between 2.5 and 3.x.
