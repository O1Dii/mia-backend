# S30 handoff

## Outcome

Clean install → real Google sign-in → conversation → streaming text answer from
real Gemini → process restart → persistent history → retry of a failed turn all
pass on a physical Samsung SM-S938B against a live-configured backend. Six
full-stack automated journeys cover the same path plus refresh, logout and
cross-account isolation. The device run exposed the blocking Gemini defect fixed
in [S17-R1](S17-R1.md).

## Scope completed

- Automated E2E over the **composed** application (`create_app` + `install_runtime_api`)
  with real PostgreSQL and real Redis, covering: Google exchange → MIA session,
  authenticated conversation create, `message:stream` deltas → completion,
  canonical history readable from a fresh application instance, idempotent retry
  with a single provider call, expired access → refresh → rotation → spent-token
  reuse revoking the family, logout failing every protected route closed, and a
  second account seeing 404 plus an empty list.
- Physical-device run of the same journey against real Gemini.

## Decisions

- The automated journeys substitute only the model boundary and Google's
  signature check, using the seams S12 and S13 already expose. Auth claim
  validation, nonce binding, rate limits, persistence and SSE all run for real.
- The device gate ran against `AI_PROVIDER=gemini`, not the fake provider. That
  is what surfaced S17-R1; a fake-provider device run would have passed and
  hidden it.

## Incomplete work

- Device logout and re-login were verified by S21-R2 at backend `b7a6c10` rather
  than re-run at the integrated head. Nothing in W6 touched the auth path.

## Open issues

- OI-W6-006: `install_runtime_api` hard-wires `GoogleIdTokenVerifier()` and the
  text provider, so full-stack tests must monkeypatch module attributes.
- OI-W6-007: `auth_access_token_ttl_seconds` has a 600 s floor, so no test can
  configure a short-lived access token; expiry is exercised by minting one.
- OI-S22-001 and OI-W5-002 remain open and were not resolved here.

## Known limitations

- No live-token Google smoke: the RSA/cert path is covered credential-free by
  `tests/auth/test_google_verifier.py` and by the real device sign-in, but not by
  an automated test against live Google certificates.
- "Process restart" in the automated suite is a fresh in-process application
  instance. The real OS-level restart was covered on the device.
