# S16-R1 handoff

## Outcome

The first real device voice session died as soon as Gemini transcribed a second
utterance: the event mapper treated a transcript fragment arriving after a final
one as a protocol violation, the receive loop raised, and the gateway answered
`realtime_provider_unavailable`. A continuing input transcript is now accepted,
and the full round trip — device speech → Gemini → response audio and transcripts
back on the device — was observed afterwards.

## Root cause

`GeminiLiveEventMapper._map_transcription` raised
`InvalidGeminiLiveMessage("Gemini appended text after a final transcript")`
whenever text arrived for a state whose transcript was already `finished`.

With automatic activity detection, Gemini transcribes continuously and is not
bound to MIA's commit boundaries: once a turn completes, `_input_state()` falls
back to `_last_state`, and the next utterance's transcription lands on that
already-final state. The very behaviour the PoC depends on — the user speaking
again — therefore killed the session. `_receive_loop` discards the original
exception, so the failure surfaced only as "provider unavailable".

## Why the suite missed it

The mapping fixtures never sent input-transcription text after `finished`. Every
scripted turn ended cleanly, so the continuation case existed only in real
traffic.

## Decisions

- Input transcription is relaxed, output transcription is not. An output
  transcript belongs to exactly one response, so text after its final fragment
  really is inconsistent; input transcription is a continuous stream that MIA
  does not control.
- The new transcript is attributed to the same state the mapper already chose for
  pre-commit fragments (`_last_state`). Attribution was not changed here; see
  OI-W6-002.
