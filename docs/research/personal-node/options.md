## 1. Форма узла и где живёт его код

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Пакет в этом репозитории** (`app/node/**` + точка входа `mia-node`), то же ядро `app/` | Одно ядро, одни миграции и тесты; узел в режиме «дома» — это тот же `create_app()` с другим профилем | Пакет узла тянет зависимости сервера (FastAPI и др.) — для ПК это приемлемо |
| B. Отдельный репозиторий | Независимые релизы | Копирование ядра или его публикация как библиотеки; расхождение версий протокола |
| C. Узел на другом языке (Go/Rust-агент) | Маленький бинарник | Ядро не переиспользуется: режимы «дома» и «вместо сервера» пришлось бы писать заново |

**Рекомендация: A.** Один процесс `mia-node`. Агент держит управляющий канал, туннель, локальные инструменты и
Ollama. С M91 тот же процесс поднимает и ядро (API + воркер в lifespan) на встроенном Postgres.

Распространение v1:

- `uv tool install mia-node` (или `pipx`) из колеса, собранного из этого репозитория;
- автозапуск: launchd на macOS, Планировщик задач или служба на Windows, unit systemd на Linux;
- Docker Compose для домашних Linux-серверов.

Нативные установщики (PyInstaller, MSI/PKG) — после пилота.

## 2. Хранилище на узле

Подробно — [postgres-inventory.md](postgres-inventory.md). Коротко:

| Вариант | Изменения ядра | Эксплуатация | Размер |
|---|---|---|---|
| **A. Встроенный PostgreSQL** (бинарники [N7], `initdb` при первом запуске, `127.0.0.1` или сокет) | ~0: тот же SQL и те же миграции | +1 процесс (~30–60 МБ); смена мажорной версии — через архив | S–M |
| B. SQLite | ~190 мест в 27 файлах + отдельная базовая миграция + вторая матрица тестов навсегда | Один файл | L + постоянные затраты |
| C. Docker Compose с теми же образами | 0 | Нужен Docker Desktop: тяжело, лицензия для организаций, не для обычного ПК | S, но только для серверов |

**Рекомендация: A для всех ОС, C — дополнительно для Linux-серверов.** `pgserver` [N6] устарел (2024,
Postgres 16.2), поэтому бинарники Postgres 16 из [N7] или EDB закрепляются по SHA-256.

## 3. Транспорт и шифрование клиент ↔ узел

Требования:

- узел не открывает входящих портов (Architecture §6);
- только проверенный протокол, без своего крипто (Review §10.1 «не добавлять собственный relay и E2EE-протокол»);
- relay не видит содержимого;
- работает в браузере и в приложении Android.

| Вариант | Как | Что видит relay | Клиенты | Инфраструктура | Вердикт |
|---|---|---|---|---|---|
| **T1. TLS 1.3 до узла через SNI-relay** | Узел держит исходящий WSS-туннель к relay. Relay читает только SNI из ClientHello и пересылает байты TLS в туннель. TLS заканчивается на узле, сертификат Let's Encrypt выписан на `<случайное>.n.<домен>`, ключ остаётся на узле. Так работает удалённый доступ Home Assistant Cloud (SniTun) [N1][N2] | Имя узла (SNI), IP клиента, объёмы и время | Браузер — нативно, без изменений; Android — OkHttp + закрепление ключа узла (pin) | Хост с «сырым» TCP 443 для relay (текущий сервер стоит за TLS-шлюзом провайдера, который сам терминирует TLS — `DEPLOY_TEST.md`); DNS-зона с API для ACME DNS-01 | **Рекомендуется** |
| T2. Noise поверх WSS | Сообщения шифруются Noise (например, KK после pairing) внутри обычного WSS через облако | Метаданные | Нужна реализация Noise в web (JS), Android (Kotlin) и Python, плюс «HTTP поверх кадров» во всех клиентах. | T3. MLS | Групповой протокол (RFC 9420) | Метаданные | Тяжело для одного пользователя с 2–3 устройствами; зрелых библиотек для браузера мало | — | Избыточно |

### Детали T1

- **Сертификат.**
  - Узел генерирует TLS-ключ (отдельный от ключа устройства) и CSR и отправляет `cert.issue` по управляющему
    каналу.
  - Облако выполняет ACME DNS-01 для `<host>.n.<домен>` своим DNS-токеном и возвращает цепочку.
  - Ключ не покидает узел.
- **Лимиты Let's Encrypt** [N5]:
  - 50 новых сертификатов в неделю на зарегистрированный домен и 5 на один набор имён. Для пилота (5–20 человек)
    этого хватает.
  - Продления через ARI от лимитов освобождены.
  - При росте зону `n.<домен>` вносят в Public Suffix List, как это сделали Plex и Nabu Casa.
- **Certificate Transparency.**
  - Имя узла попадает в публичные журналы. Поэтому оно случайное (`n` + 16 символов base32) и не содержит имени
    человека или компьютера (так же предупреждает Tailscale [N9]).
  - Оператор Mia управляет DNS и технически может выписать второй сертификат на то же имя: это атака
    «человек посередине» для браузера.
  - Защита:
    - приложение Android закрепляет SPKI ключа узла, полученный в подписанном узлом манифесте (подпись проверяется
      по отпечатку из QR);
    - узел может следить за CT-журналами своего имени (после пилота);
    - честная формулировка на странице «Где ваши данные».
- **Relay** — небольшой сервис `mia-relay` (Python asyncio):
  - TCP 443: разбор SNI и пересылка потоков;
  - WSS: туннели узлов;
  - мультиплексор без собственного шифрования — шифрует TLS клиента внутри и TLS туннеля снаружи.
  - SniTun [N2] — готовая реализация, но под GPL-3.0; Mia пишет свою (мультиплексирование — не криптография,
    ~400 строк) либо принимает GPL для отдельного сервиса relay (решение пользователя не требуется, выбор M91).
- **LAN.**
  - Приложение Android может подключаться к LAN-адресу узла (найденному через mDNS) с тем же SNI и pin —
    напрямую, без relay.
  - Браузер в LAN идёт через relay, если пользователь не настроил локальный DNS. На самом ПК есть
    `https://localhost:<порт>`.

## 4. Pairing, ключи, отзыв

- **Ключ устройства узла** — Ed25519.
  - Хранится в хранилище ОС через `keyring`: macOS Keychain, Windows Credential Locker, Secret Service.
  - На headless Linux — файл с правами 0600.
  - Ротация — `node.rotate_key`, подписи старым и новым ключом.
- **Pairing по QR** (`contracts/node/v1/pairing.schema.json`):
  1. Узел регистрирует публичный ключ.
  2. Облако выдаёт `pairing_id`, код `XXXX-XXXX` (10 минут) и `poll_token`.
  3. Узел показывает QR: `pairing_id`, код, отпечаток ключа и хост API.
  4. Приложение сканирует QR, либо web принимает код (тогда пользователь сверяет отпечаток с экраном узла).
  5. Облако привязывает ключ к аккаунту только при совпадении отпечатка.
  6. Узел, опрашивающий с подписью, получает `node_id` и адрес управляющего канала.
  - Подмена ключа сервером при сканировании QR обнаруживается.
- **Вход узла в канал.** Challenge–response: одноразовый nonce, подпись с разделением доменов, привязка к
  `connection_id`. Секрета-«пароля» на узле нет.
- **Номера последовательности и защита от повтора** — `contracts/node/v1/README.md`:
  - `seq` по направлению, `ack`, resume с буфером 256 кадров или 60 с;
  - кеш выполненных `tool.call` на 24 ч;
  - `deadline_at`;
  - сверка `args_hash`.
- **Отзыв** («Отключить» в «Устройствах» или `mia-node unpair`):
  - статус `revoked`, кадр `revoked` и close 4403;
  - новые подключения с этим ключом отвергаются;
  - гранты ADR-0016 на этот узел удаляются;
  - сертификат отзывается, DNS-запись снимается;
  - узел стирает ключ и токены. Данные дома остаются на диске, и узел прямо об этом пишет.
- **Отзыв клиента узлом** (режимы home/standalone): в локальном списке устройств узла, тот же механизм
  refresh-семейств, что в облаке (M10).

## 5. Согласие на действия на ПК (ADR-0016)

Узел — ещё одно устройство политики `allow | ask | deny`: (capability, requester, target = узел, scope).
ADR-0016 §4 требует давать согласие **на целевом устройстве**. Но у ПК часто нет человека перед экраном (запрос
пришёл с телефона из другой комнаты), а у домашнего сервера экрана нет вовсе.

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **a. На телефоне владельца** (назначенный «подтверждающий») | Тот же лист согласия M71 и push с кнопками; в тексте — «Домашний ПК: поиск файлов в «Документы»» | Работает для headless-узла; повторно использует M70/M71 целиком; человек обычно с телефоном | Отступление от буквы ADR-0016 §4. Украденный разблокированный телефон может разрешить чтение разрешённых папок |
| b. На самом ПК | Уведомление рабочего стола + локальная страница `https://localhost:…/approve` | Буква ADR-0016 | Кросс-платформенные уведомления с кнопками из Python ненадёжны; человека у ПК часто нет; не работает для сервера |
| c. Где удобнее (телефон или ПК) | Оба места, первое решение побеждает | Гибко | Больше UI и тестов |

**Рекомендация: a по умолчанию, c — настройка узла позже.** Обязательная граница безопасности:

- папки, программы и включённые возможности задаются **только на самом узле** (локальная конфигурация или CLI
  `mia-node folders add …`), облако не может их расширить;
- согласие выбирает только внутри этой границы;
- по умолчанию запрещены скрытые и «секретные» файлы: `.env*`, `.ssh`, `*.pem`, `id_*`, `*.kdbx`, хранилища
  браузеров и ключей;
- файлы только читаются — запись и удаление в v1 не делаются;
- чтение файла — `read` (постоянный грант до 30 дней разрешён); открыть программу или ссылку — `action`;
- внешних действий у узла в v1 нет.

## 6. Ollama через узел

- **Связь с Ollama.**
  - Ollama слушает `localhost:11434` и даёт OpenAI-совместимый `/v1/chat/completions` с потоковой выдачей и
    tools [N3].
  - `tool_choice` не поддерживается [N3].
  - Размер контекста через OpenAI-API не задаётся — только Modelfile (`num_ctx`).
- **Облачный runtime (data_mode `cloud`)**:
  - адаптер `node-ollama` в Model Gateway шлёт `model.generate` по управляющему каналу;
  - узел транслирует поток в `rpc.stream`, а адаптер превращает его в `TextDelta` / `ToolCallRequested` /
    `ModelUsage` / `ModelDone`.
- **Runtime на узле (home/standalone)** использует существующий провайдер `ollama`. Его нужно перевести с
  `chat_only` (сейчас `ChatOnlyAdapter`, без потока и tools) на `chat_completions`.
- **Лимиты ADR-0011.**
  - Run engine сейчас не задаёт `max_output_tokens` — M88 вводит его по профилю.
  - Узел дополнительно соблюдает `deadline_at`, `first_token_timeout_ms` и `rpc.cancel`.
  - Одна генерация за раз (`max_concurrent_generations`), иначе `node_busy`.
  - Для голоса — `model.warmup` при открытии голосового режима и `keep_alive`, потому что холодная загрузка 8B-модели
    занимает секунды, а цель — первый звук около 6 с.
- **Без тихого отката.**
  - Подключение «Модель на ПК» не входит в цепочку резервов `mia:default`.
  - Если пользователь выбрал её основной, а узел выключен, шаг падает с `node_offline` и понятным текстом.
  - Резерв на облачную модель включается только явной настройкой (Architecture §6 «пользователь заранее настраивает
    допустимый fallback»).
- **Честность.** В режиме `cloud` промпт для Ollama собирает облачный runtime, поэтому **сервер Mia видит текст**.
  Локальная модель защищает от стороннего провайдера, а не от оператора. Полную приватность дают режимы
  home/standalone.

## 7. Данные дома (режим `home`)

| Данные | Режим `cloud` (сейчас) | Режим `home` |
|---|---|---|
| Аккаунт (Google `sub`, e-mail), сессии входа в облако | облако | облако |
| Реестр устройств и узлов, публичные ключи, push-токены | облако | облако |
| Маршрутизация relay, DNS, учёт сертификатов | — | облако |
| Каталог магазина (публичный) | облако | облако; узел скачивает пакеты |
| Чаты, сообщения, runs и события, сводки | облако (DEK) | **узел** |
| Память: факты, люди, предпочтения; журнал доступа | облако (DEK) | **узел** |
| Задачи, расписания, «Входящие», результаты | облако | **узел** |
| Установки плагинов, их состояние, OAuth-токены плагинов | облако | **узел** |
| Ключи моделей и подключения | облако (DEK) | **узел** (хранилище ОС) |
| Метаданные в облаке о содержимом | — | ничего: ни заголовков чатов, ни счётчиков; только «данные аккаунта на узле X», время последнего контакта |

**Когда узел выключен:**

- клиенты показывают «Компьютер не в сети — история и память недоступны», ответ `node_data_unavailable`;
- новый чат в облаке без памяти — только явной кнопкой «Временный чат в облаке», с меткой; это не тихий откат;
- задачи и расписания выполняются на узле; после включения работает политика пропусков M16
  (`skip` / `run_once` / `limited_catch_up`);
- напоминания и таймеры, которые должны сработать, пока узел выключен, — решение пользователя Р6.

**Синхронизация.** Один писатель — узел. Мультимастера нет (Architecture §11: один владелец записи). Клиенты
только кешируют. Переход облако → узел и обратно — явная миграция архивом.

**Бэкап.**

- Ежедневный `pg_dump` и файлы рабочей папки шифруются форматом age [N11] (вызов из Python — pyrage [N12]) в папку,
  которую выбрал пользователь: внешний диск, NAS, папка облачного диска.
- Ключ восстановления показывается один раз и хранится в хранилище ОС.
- Есть команда проверки восстановления `mia-node backup verify`.
- Хранение: 7 ежедневных и 4 еженедельных копии.

## 8. «Узел вместо сервера» (режим `standalone`)

**Вход.**

| Вариант | Как | Когда |
|---|---|---|
| a. Аккаунт Mia остаётся | Узел — OAuth-клиент «Войти через Mia» (ADR-0013). Браузер на адресе узла проходит вход в облаке, узел проверяет ID token (ES256, JWKS) и `sub` владельца. Android получает от облака короткое подписанное «приглашение» для узла | Режим `home`; standalone при доступном облаке |
| **b. Без облака** | Первый владелец — по одноразовому коду или QR с экрана самого узла (`https://localhost`). Дальше Android входит ключом устройства (pairing с узлом), браузер — passkey (WebAuthn на имени `<host>.n.<домен>` с настоящим сертификатом: RP ID — домен, IP-адрес нельзя [N13]) | Standalone |
| c. Google прямо на узле | Узлу нужен свой OAuth-клиент Google, а значит, проект в Google Cloud у пользователя; подстановочные origins Google не принимает | Не рекомендуется |

**Push.**

| Вариант | Как | Минусы |
|---|---|---|
| **a. Push-прокси Mia без содержимого** | `push.send` → FCM-проект Mia → приложение просыпается и забирает данные с узла по сквозному TLS | Нужна связь с облаком; облако видит факт и время уведомления |
| b. Без push | Приложение проверяет узел, пока открыто | Напоминания при закрытом приложении не доходят |
| c. UnifiedPush (ntfy) | Свой сервер push у пользователя | Ещё один сервис; отдельная работа в Android |

Ключи FCM — секрет проекта Mia, поэтому узел не может отправлять в FCM сам.

**Бот Telegram.**

| Вариант | Как | Что видит облако |
|---|---|---|
| **a. Свой бот пользователя на узле** | Токен от BotFather хранится на узле, обновления забираются long polling `getUpdates` — публичный адрес не нужен [N14] | Ничего (Telegram видит сообщения, как всегда) |
| b. Бот Mia через облако | Облако получает webhook и пересылает узлу | Текст сообщений проходит через облако |
| c. Выключен | — | — |

**Телефон вне дома:** relay (T1) — по умолчанию; Tailscale (T4) — опция; проброс портов и DDNS — не
рекомендуется. В LAN — напрямую (§3).

**Перенос облако ↔ узел** — архив `mia-archive/v1`:

- состав: `manifest.json` (версия схемы = Alembic head, счётчики, SHA-256 файлов) + JSONL по сущностям; память
  экспортируется расшифрованной и запечатывается заново ключом узла;
- порядок:
  1. «заморозка» аккаунта (запись запрещена, `account_migrating`);
  2. узел скачивает архив по TLS у облака;
  3. импорт, сверка счётчиков и хешей, смоук;
  4. пользователь подтверждает → облако переключает `data_home` и криптографически уничтожает содержимое (DEK,
     как в M17);
  5. разморозка;
- при сбое до шага 4 облако размораживается, и ничего не теряется;
- обратный путь — `POST /v1/account/archive`;
- миграции схемы между версиями: узел и облако применяют один и тот же `alembic upgrade head`, потому что
  хранилище одно и то же — встроенный Postgres (§2).
